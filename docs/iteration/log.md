## Cycle 43 · 2026-11-14 · 共识的相邻财年隐含增长

**对应卡片**：P1-1 遗留（共识只比修订，不算增长）

**问题**：一致预期此前只能回答「同一目标期间的共识被上修还是下修」，不能回答「共识自己预期明年增长多少」。后者才是与分析师的增长假设、反向 DCF 的隐含增长对话时真正需要的东西。

**改动**

| 文件 | 变更 |
| --- | --- |
| `scripts/consensus.py` | 新增 `period_growth`：同序列、同提供方、相邻财年时，取各期最新快照中位数计算隐含增长；不满足条件跳过并 warning |
| `scripts/render_report.py` | 共识快照表后新增「相邻财年的隐含增长」表 |
| `tests/test_consensus.py` | 6 个单元用例（连续财年、非连续、提供方不一致、指标标签不一致、零基期、使用最新快照）+ 1 个渲染用例 |
| 文档 | expectations / memo-template；CHANGELOG 0.45.0 |

**关键设计决定**

1. **只在严格条件下计算**：同序列、同提供方、年份连续、指标标签一致、基期非零。任何一个不满足就跳过并说明，而不是「尽量算一个」。
2. **只认 FY 标签**：`FY2026` 可解析，`next quarter`、`2027Q1` 不推断——季度财报的财季对应关系依公司而异，猜会错。
3. **取最新快照**：同一财年有多次快照时用最新中位数，符合「当前共识」的语义；旧快照仍用于修订计算。
4. **明示不是判断**：渲染时写「这是共识自己的算术，不是研究判断」——把共识外推与研究者判断分开。

**验证证据**

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests
# Ran 468 tests ... OK
```

- 连续财年：FY2026 中位 10 → FY2027 中位 12，隐含增长 0.2，端点 claim 正确。
- 跳过：FY2025→FY2027（不连续）、提供方 LSEG vs FactSet、指标 `EPS` vs `EPS (adj)`、基期中位为 0，全部不产出并给 warning。
- 最新快照：FY2026 有 9（9月）与 10（10月）两次快照，用 10 计算 → 0.2，`from_claim` 指向后者。
- 非 FY 标签：`next quarter`、`2027Q1` 不产生任何行。
- 渲染：附录出现「相邻财年的隐含增长」「共识隐含增长」，隐含增长 0.2。
- 冻结示例：`report.md` / `report.html` 逐字节相同。

**投研意义增量**

1. 多一个可直接对话的量：共识隐含增长 vs 反向 DCF 隐含增长 vs 研究假设。
2. 多一条可核实连接：每个隐含增长两端都指向具体 claim。
3. 边界更清楚：条件不满足就不算，FY 之外的标签不猜。

**遗留**

- 季度序列的环比/同比增长未做（需要财季日历）。
- 没有把隐含增长与 `reverse_dcf` 的 implied_growth 自动并排；两者期限不同，直接并列容易被误读。
- 隐含增长未进入 memo 一页纸。

**对应卡片**：P1-4f 遗留（堆叠柱状）

**问题**：分组柱状能对比，但不能表达构成。分部收入占比、成本结构这类图没有合适的画法。

**改动**

| 文件 | 变更 |
| --- | --- |
| `scripts/render_report.py` | `chart.bar_mode`：grouped（默认）/ stacked；堆叠自下而上按系列、透明度区分；校验要求 series 且非负 |

**关键设计决定**

1. **负值直接拒绝**：正负混合的堆叠柱会让人误读总量与构成，宁可报错要求改成分组柱。

3. **表格权威**：堆叠柱只表达结构，精确值在同源表；表格列与分组柱一致。
4. **缺省零变化**：不写 `bar_mode` 时分组柱、折线、瀑布渲染字节不变。

**验证证据**

```bash

# Ran 461 tests ... OK
```

- 堆叠：2 系列 × 2 标签 → 4 个 `<rect>`；页面出现「堆叠柱状」「堆叠顺序（自下而上）」「云 · FY2025 8 亿元」；表头「期间 | 云（亿元） | 设备（亿元）」。
- 负例：stacked 无 series、series 含 −1、bar_mode 用在 line 上全部拒绝。
- 分组柱状、单序列柱状、折线、瀑布均无回归；冻结示例逐字节相同。

**投研意义增量**

1. 多一种表达：构成与占比。
2. 边界更清楚：堆叠只接受非负、顺序显式。
3. 口径可靠：数值仍以同源表为准。

**遗留**

- 堆叠没有百分比模式（100% 堆叠），占比图要自己先算比例。
- 系列数超过 4 时透明度差异变小。
- 堆叠柱未进入 memo 一页纸。

## Cycle 41 · 2026-11-14 · 别名冲突检测

**对应卡片**：P0-6c 遗留

**问题**：别名表上一版是「后者覆盖前者」——两个规范名共享同一别名时，结果取决于字典顺序，且没有任何提示。用户会看到实体分组不对，却不知道原因。

**改动**

| 文件 | 变更 |
| --- | --- |
| `scripts/research_memory.py` | 规范名排序遍历；冲突先到先得并写 warning；别名值非数组时只保留规范名 + warning |
| `tests/test_research_memory.py` | 2 个用例：双向别名冲突、非法别名值 |
| 文档 | research-memory 补冲突规则；CHANGELOG 0.43.1 |

**关键设计决定**

1. **先到先得 + 字母序**：结果可预测、可复现，不依赖 JSON 书写顺序。
2. **冲突是 warning 不是 error**：别名是辅助功能；一个冲突不该让整个索引失败，但必须让人看见。
3. **冲突信息带双方名字**：warning 直接写 `maps to both 'NVDA' and 'NVIDIA'`，用户知道要改哪两条。

**验证证据**

```bash

```

- 冲突：`{"NVDA": ["NVIDIA"], "NVIDIA": ["NVDA"]}` → warnings 两条（nvidia、nvda 各一），`alias_map["nvidia"] == "NVDA"`（字母序先到）。
- 非数组：`{"NVDA": "NVIDIA"}` → warning「must be a list」，规范名本身仍注册。
- 冻结示例：`report.md` / `report.html` 逐字节相同。

**投研意义增量**

1. 实体归并结果可预测、可解释。
2. 数据问题从「静默错分」变成「显式 warning」。

**遗留**

- 没有「建议别名」功能（从已有 run 的实体变体里自动提议）。
- 冲突解决仍需用户手工改文件。

## Cycle 40 · 2026-11-14 · 数据根体检 doctor

**对应卡片**：P2-7（新增；升级/迁移的运维入口）

**问题**：插件更新频繁，契约也在收紧。用户升级后没有一键检查「我的数据根还健康吗」的入口；只能逐个打开归档或等某个命令报错。归档兼容性此前只有测试在守，用户侧没有工具。

**改动**

| 文件 | 变更 |
| --- | --- |
| `scripts/doctor.py`（新） | 用当前校验器加载每个归档；重建记忆索引（实体/别名/跳过）；统计催化 dated/undated/overdue；只读；退出码 0/1/2 |
| `tests/test_doctor.py`（新） | 9 个用例：健康、过期 warning、坏档失败、空目录、只读快照、CLI 退出码、TOUYAN_HOME 默认根 |
| 文档 | 安装指南「数据根体检」；architecture 入口；CHANGELOG 0.43.0 |

**关键设计决定**

1. **只读不修**：体检工具最怕「顺手帮你改」；这里明确不写缓存、不改归档、不自动修复，测试用相对路径哈希快照守。
2. **归档失败才算 error**：催化无日期、已过期都是 warning——它们是数据形态，不是损坏；把 warning 当 error 会让用户以为要修什么。
3. **退出码分层**：0 健康 / 1 有归档不可读 / 2 根目录或 journal/runs 不存在；脚本化调用可直接判断。
4. **用真实归档写测试**：测试通过 `archive_run` 建真档案，而不是手写 manifest，避免「测试通过但真实归档路径不同」。

**验证证据**

```bash

python3 scripts/doctor.py --home . --as-of 2026-11-14
```

- 本机真实数据根：25 个归档全部加载、0 失败、15 个实体、121 条催化全部无日期（旧 run 只有自由文本 `by`），退出码 0。
- 坏档：目录里有损坏 report.json → 该 run 进入 errors，其余照常统计，退出码 1。
- 过期：watch due 2026-11-12、参考日 2026-11-14 → overdue 1，warning 文案明确「过期表示未核对，不是未触发」。
- 只读：体检前后数据根所有文件哈希一致。
- 冻结示例：`report.md` / `report.html` 逐字节相同。

**投研意义增量**

1. 多一个运维入口：升级/迁移后可以先体检，再决定是否深入。
2. 多一条用户侧兼容保证：不依赖开发者跑测试。
3. 边界更清楚：只读、只报、分类 warning 与 error。

**遗留**

- 不检查 `journal/work` 与旧 `memos.jsonl` 等历史目录。
- 不估算数据体积，也不提示清理策略。
- 体检不检查插件是否被宿主加载（那需要宿主侧信息）。

## Cycle 38 · 2026-11-14 · 用真实报表验证固定模型

**对应卡片**：真实参数演练（我先前自己列的计划）

**问题**：测试一直只证明「模型按定义运行」，不能证明「定义本身合理」。`operating_bridge` 的效应拆解与 `driver_build` 的分部加总，从未在真实损益表上对过账。

**做法**：拿微软 FY2024/FY2025 已披露的数字（来自示例里已冻结的官方表格），分别构造两个模型的输入，看输出能否复现官方报表。

**结果**

| 模型 | 输入 | 输出 | 官方披露 |
| --- | --- | --- | --- |
| operating_bridge | 基期收入 245,122、营业利润率 44.64%、增长 14.93%、情景利润率 45.62% | 收入 281,724、营业利润 128,528、变化 19,095 | 281,724 / 128,528 / 19,095 |
| driver_build | 三大分部实际增速、FY2025 分部利润率、价增长 0 | 收入 281,724、营业利润 128,528、增量利润率 46.3% | 同上 |

`operating_bridge` 的「收入效应 + 利润率效应」恰好等于利润变化，说明拆解没有重复计入或遗漏。

**改动**

| 文件 | 变更 |
| --- | --- |
| `tests/test_analysis_models.py` | `RealDataTests`：两个模型对真实报表的复现断言 |
| `examples/msft-quality/segments.json`（新） | 三大分部 FY2024/FY2025 收入与营业利润，标注来源 |
| `examples/msft-quality/README.md` | 新增「用固定模型复现官方报表」一节 |
| CHANGELOG | 0.41.0 |

**关键设计决定**

1. **用官方披露做端到端断言**：不是拿模型和自己比，而是拿模型和损益表比。任何口径错误（例如把毛利用成营业利润、把分部利润率当成合并利润率）都会让断言失败。
2. **价增长置 0**：官方只给分部收入，没有量价拆分；把无法观测的部分显式设为 0，而不是编一个量价假设。这样「增量利润率」只反映实际收入增长与利润率，不掺假设。
3. **分部数据独立成文件**：来源与期间写在文件里，测试读取而不是把数字硬编码进断言，便于核对与更新。

**验证证据**

```bash

```

- bridge：revenue 281,724.0、profit 128,528.0、change 19,095.0（误差 < 1e-6）。
- driver：revenue 281,724.0、profit 128,528.0、revenue_growth 0.149322、incremental_margin 0.463271。
- 冻结示例：`report.md` / `report.html` 逐字节相同。

**投研意义增量**

1. 模型的可信度从「定义自洽」提升到「能复现真实报表」。
2. 口径错误的防线：分部加总、利润率选择、效应拆解都被真实数字检验。
3. 例子从「展示输入」升级为「可执行的验证」。

**遗留**

- 只验证了 `operating_bridge` 与 `driver_build`；DCF/反向 DCF 需要现金流与折现假设，无法用损益表直接复现。
- 价增长置 0 是简化，真实量价拆分仍缺数据。
- 分部数据只有三家，无法覆盖更细的产品线。

## Cycle 22 · 2026-11-14 · 模型输入与 metric 的数值一致性

**对应卡片**：P1-0c

**问题**：模型 observed 输入引用 claim 时只校验类型，数值从不比对。一条「收入 1200」的 claim 可以被当成「capex 60」的证据写进模型，两边都能通过校验；这正是审计一开始指出的「数字层不可核验」的最后一环。

**改动**

| 文件 | 变更 |
| --- | --- |
| `scripts/analysis_contract.py` | 量纲映射（currency / ratio / shares / currency/share）、缩放解析（万/亿/千/百万/十亿/万亿等中英写法）、换算后比较（相对 1e-9）；无法解析则跳过 |
| `tests/test_analysis_contract.py` | 4 个用例：金额匹配/数值不符/量纲不符/缩放不可解析；股本匹配与不符；每股匹配与不符 |
| 文档 | analysis-methods 与 memo-template 补规则；CHANGELOG 0.26.0 |

**关键设计决定**

1. **量纲不符直接失败**：这不是数值误差，而是引用错误证据。把 ratio 当 currency 输入、把股本当金额输入，说明 claim 选错了。
2. **缩放无法解析时跳过而不是猜**：wrapper.scale 是自由文本（「million (money and shares)」「金额百万美元」），解析不到倍数就保持通过并保持沉默。宁可少查一次，也不制造必须解释的假错误。
3. **price 不走金额缩放**：每股价格本来就是每股口径，乘不乘金额倍数都会错；只比较原始每股数值。
4. **只在 observed 输入触发**：assumption 输入引用的是 inference/view，本来就没有「原文数值」可比。
5. **旧档案零影响**：没有 metric 的 claim 不触发；有 metric 但未被引用的也不触发。真实归档全部通过。

**验证证据**

```bash

# Ran 401 tests ... OK
```

- 金额：C1 metric 100 USD million、wrapper scale million、输入 100（currency）→ 通过；把 metric 改 120 或 scale 改 thousand → 失败并给出两边数值。
- 量纲：C1 metric unit 改成 ratio 后作为 currency 输入 → `unit currency differs from the metric unit ratio`。
- 缩放不可解析：wrapper.scale 改成「same scale as the statement」且 metric 值明显不符 → 通过（不猜）。

**投研意义增量**

1. 多一条可核实连接：模型里的每个 observed 数字第一次能和 claim.metric 对上，而不仅是「引用了一个 claim」。
2. 多回答一类问题：「这个输入引用的证据数值真的是这个吗」。

**遗留**

- metric 的 `unit` 仍是自由文本，靠关键词映射；若出现「per ADS」「per class A share」等特殊每股口径，会被跳过（无法识别）而不是误判。

## Cycle 21 · 2026-11-14 · 行业传导图

**对应卡片**：P2-4（新增；目标里的「行业传导」）

**问题**：主题研究里「需求 → 产能 → 交付 → 毛利」通常是一段话：断点靠感觉，机制没有方向，时滞没有窗口，读者无法核对哪一环最可能断。

**改动**

| 文件 | 变更 |
| --- | --- |
| `scripts/transmission.py`（新） | 节点/边/瓶颈校验；方向（upstream/downstream/bottleneck/unrelated）、跳数、源头到瓶颈路径；无关节点、环路、无证据节点告警；可选 `--claims` 核对引用 |
| `tests/test_transmission.py`（新） | 11 个用例：形状、引用、方向/距离/路径、多源头、无关节点、环路、无证据节点、CLI |
| 文档 | 新增 [transmission.md](../../skills/research/references/transmission.md)；SKILL、architecture；CHANGELOG 0.25.0 |

**关键设计决定**

1. **方向比「排一条链」重要**：第一版把不能到达瓶颈的节点都叫「可能只是背景」，但瓶颈**下游**的节点（交付、毛利）本来就到不了瓶颈，却被误报。改成 upstream/downstream/bottleneck/unrelated 四种方向后，告警只针对真正无关的节点。
2. **瓶颈由研究者指定**：工具不自动挑「最重要的节点」。换瓶颈会让所有方向判断翻转，这个选择必须写在正文里。
3. **跳数不是时间**：`lag` 是每条边的时间窗口，工具不做加总、不换算成一条时间线——那会制造不存在的精度。
4. **环路只提示**：价格与需求可能真的互相反馈；把环路判成错误会逼研究者隐藏真实的反馈关系。
5. **observables 必须可核对**：空泛的「景气度」不接受，至少要有订单、排队时长、交付周期这类可观察项。

**验证证据**

```bash

# Ran 398 tests ... OK
```

- 示例链 DEMAND→GRID→EQUIP→MARGIN，瓶颈 GRID：方向为 upstream(DEMAND)、bottleneck(GRID)、downstream(EQUIP, MARGIN)，距离 DEMAND=1，路径 [[DEMAND, GRID]]。
- 多源头：PRICE→GRID 追加后两条路径；POLICY→DEMAND 追加后距离 2、路径 [[POLICY, DEMAND, GRID]]。
- 无关节点：新增无连线的 ISOLATED → direction unrelated 且出现在告警里。
- 环路：EQUIP→DEMAND → 告警含「环路」，输出正常返回不死循环。
- 无证据：移掉 DEMAND 的 claim_ids → 告警列出该节点。
- 校验：未知 kind、空 observables、悬空 edge、自环、重复边、瓶颈缺失、未知 claim（带 --claims 时）全部拒绝。
- 冻结示例：`report.md` / `report.html` 逐字节相同。

**投研意义增量**

1. 多一种分析师会用的方法：行业传导图 + 瓶颈定位，而不是一段叙述。
2. 多回答一类问题：「这条链最可能在哪一环断、用什么指标核对、哪些环节其实无关」。
3. 多一条可核实连接：节点与边都可挂 claim_ids，`--claims` 会核对是否真实存在。
4. 边界更清楚：不判机制真假、跳数不等于时间、瓶颈是研究者的选择。

**遗留**

- 没有渲染进报告：目前是独立产物，把图写进正文仍需研究者组织。
- 时滞不做加总，也没有「整条链总时滞」的区间推导；这是有意的，但如果要，需要区间算术而不是图算法。

## Cycle 20 · 2026-11-14 · 判断沿革（thread）

**对应卡片**：P0-6 遗留项（论点跟踪）

**问题**：「跨轮研究记忆」已经能回答「关于 X 我们判断过什么」，但没有把每轮的 `parent_run` 还原成一条沿革：读者看到的是并列的 run 列表，看不出「这一轮改了什么、上一轮判断原文是什么」。

**改动**

| 文件 | 变更 |
| --- | --- |
| `scripts/research_memory.py` | 新增 `thread --home DIR <run_id>`：按 parent_run 回溯 lineage（旧→新），带判断原文、judgment_changed、模型种类、机会状态与 depth；附直接子轮 |
| `tests/test_research_memory.py` | 6 个用例：三轮回溯、子轮、未知 run、缺父轮、循环保护、CLI |
| 文档 | research-memory 增判断沿革章节；CHANGELOG 0.24.0 |

**关键设计决定**

1. **只回溯祖先，不自动串联分支**：同一父轮可能有两个子轮（例如同时做资金面与技术面更新），把它们拼成一条时间线是编造顺序。`children` 明确列出并列子轮。

4. **循环保护**：manifest 被手工改坏可能出现 A→B→A，访问集合保证回溯终止。

**验证证据**


- 三轮回溯：A(中性) → B(转空, judgment_changed=true) → C(维持偏空, false)，`thread C` 输出顺序、判断原文与开关全部正确。

- 缺父轮：parent 指向不存在的 run → 沿革只含自身。

1. 多一种持续性工作流：判断沿革可读，更新时知道「上一轮到底说了什么」。
2. 多回答一类问题：「这次改的是哪一段判断、之前改过几次」。
3. 边界更清楚：分支不合并、不看文本 diff、缺父轮不假装完整。

**遗留**

- 沿革不带每轮的关键证据摘要（claims 数量已在索引，但未在 thread 输出）。

5. **不做概率加权**：没有概率、没有期望值、没有区间当作预测——与仓库一贯的「不制造精确性」一致。

## Cycle 10 · 2026-11-14 · 龙卷风敏感性

**对应卡片**：P1-3 的前半（情景集仍未做）

**问题**：单参数敏感性此前平铺成一张「变量 / 改为 / 输出 / 结果」的长表。读者看不出哪个假设真的要紧——DCF 里折现率、增长与终值三个输入的影响相差数倍，但表格一视同仁。

**改动**

| 文件 | 变更 |
| --- | --- |
| `scripts/analysis_models.py` | 新增可选 `spec.tornado`：`{output, inputs:[{input, low, high}]}`；逐输入推到两端，输出 `result.tornado` 按 `swing` 降序 |

**关键设计决定**

1. **`output` 必须显式指定**：不同问题关心的输出不同（每股价值、利润、隐含增长率）。默认第一个输出会让排序失去意义。

## Cycle 9 · 2026-11-14 · 价格时效与来源冲突

**对应卡片**：P1-2

**问题**：两处证据处理靠人记得。第一，市场评估可以用一份很旧的报价当「现价」——现有校验只禁止「报价晚于主张」，不禁止「报价太早」。第二，同一指标多个来源数值不一致时，报告通常只留下被采用的那一个，分歧与取舍理由消失。

**改动**

| 文件 | 变更 |
| --- | --- |
| `scripts/analysis_contract.py` | 市场评估新增价格时效校验：`quoted_at` 与 `claim.as_of` 间隔不得超过 `market.price_max_age_hours`（默认 96，1–8760）；无 sources 时跳过 |
| `scripts/render_report.py` | 新增可选 `report.conflicts[]` 的校验与附录渲染：候选来源值、采用主张、单位、规则、理由 |
| `tests/test_freshness_conflicts.py`（新） | 11 个用例：新鲜/过期报价、96 小时边界与自定义阈值、非法阈值、无 sources 跳过、冲突形状、采用主张类型、metric 数值与单位匹配、双格式渲染、无冲突兼容 |
| 文档 | analysis-methods 价格时效规则；memo-template conflicts 契约；SKILL 与研究价值参考同步；CHANGELOG 0.14.0 |

**关键设计决定**

1. **默认 96 小时而不是 24**：股票周末与长假会让 24 小时规则误伤正常的周一报告；日内/加密研究应在 `market.price_max_age_hours` 显式收紧到 24。规则可调比硬编码更不容易被绕过或误伤。
2. **只约束市场评估**：历史研究把 `as_of` 设在当时，报价与截点同时代即可；不把「旧报价」一律判错，避免把回溯研究逼成造假。
3. **冲突必须数值真的不同**：两个候选相同值不叫冲突，直接拒绝；否则这个字段会变成表演性严谨。
4. **采用主张要能对上**：若 adopted claim 带 `claim.metric`，其 unit 必须与冲突单位一致、value 必须等于某个候选值——防止「记录了冲突，采用的却是第三个数字」。
5. **无 sources 时不静默通过吗？** `validate_analysis` 在无 sources 调用时无法取报价时间，只能跳过并明确这是调用路径限制；归档与渲染路径都带 sources，检查是生效的。

**验证证据**

```bash

# Ran 310 tests ... OK
```

- 时效：报价晚于截点 0 小时通过；正好 96 小时通过；96.5 小时失败 `quotes a 96.5 hour old price; max is 96`；把阈值改 1000 后 200 小时也通过。
- 阈值：0 / 10000 / True / "24" / None 全部拒绝。
- 冲突：两个来源 12 vs 10 通过并渲染「来源冲突与取舍」；同值拒绝；未知 source / 未知 adopted claim / inference 采用 / 缺 unit / 多余字段 / 字符串数值全部拒绝；采用主张 metric=12 与候选 11 不一致时失败；unit 为 percent 与冲突单位不符时失败。
- 冻结示例：`report.md` / `report.html` 逐字节相同，22 个文件哈希匹配。

**投研意义增量**

1. 多一条证据纪律：过期报价不再能撑起「当前价格隐含什么」的判断。
2. 多一条可核实连接：来源分歧有结构化记录，读者能看到未采用的数字与取舍规则。
3. 边界更清楚：历史研究不被误伤，日内研究可显式收紧。

**遗留**

- 时效目前只覆盖市场评估的 price claim；consensus（如 45 天）与 filing（一个报告期）的陈旧度仍未系统检查。
- conflicts 只做记录与校验，不会自动比对 claims 里的同名 metric 值；下一步可让 `claim.metric` 同名同口径的差异自动提示登记冲突。
- 未提供「冲突未解决」的阻断级别；当前是可选项，靠研究纪律使用。
