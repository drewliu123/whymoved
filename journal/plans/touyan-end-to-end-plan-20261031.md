# 投研助手端到端改造方案

日期：2026-10-31
状态：讨论稿；本文件只提出产品与实现方案，未修改插件，未发布 GitHub Issue 或 PR。
依据：本地投研助手 0.2.0、Last 30 Days 3.30.0 的已核查实现，以及两版 NVDA 实跑与用户阅读反馈。

## 1. 产品目标与首版边界

用户提出一个研究问题，投研助手自动完成问题拆解、资料获取、计算、研究综合、审查、图文生成和本地交付。用户应首先看懂：发生了什么、哪些变化最重要、当前更支持什么解释、接下来什么证据会改变判断。

默认交付是对话里的短答与一份可直接打开的 HTML 研究简报。按需导出 Markdown 和一页 PNG。全部输出来自同一份研究内容与数据。简单问题可以直接用文字回答，不为凑模板生成长报告或图表。

建议首版聚焦美股个股，覆盖近期走势、财报解读、市场预期三个高频任务。沿用现有 event_pricing / asset / theme / actor 路由作为扩展基础；宏观、主题、加密、A/H 股的专用数据与页面在后续阶段接入，不将一个美股模板套给所有问题。

首版不包含交易执行、个人资产配置、实时行情终端、全市场扫描和自动对外发布。持续跟踪在单次研究链路稳定后再做。

## 2. 当前需要改的结构

| 当前结构 | 对成品的影响 | 改造方向 |
|---|---|---|
| 按资产类型固定角度拆解 | 用户问近期下跌，正文可能优先谈财报概率 | 在对象类型之上增加研究任务；按用户问题生成必须回答项 |
| fact-collector 统一取官方、预期、媒体 | 来源清单存在，但行情、指标和预期容易只剩零散摘录 | 建立官方披露、行情、预期与估值、新闻、社区五类适配接口 |
| community-scout 主要返回帖子 | 引擎的主题聚类、代表内容和覆盖信息传递不足 | 保留帖子、主题、代表原文、来源状态与查询记录 |
| 证据校验后直接组织备忘录 | 缺少筛选重要变化与解释机制的步骤 | 增加研究综合与编辑职责 |
| 正文逐句堆 C 编号、反复强调限制 | 阅读主线被过程信息打断 | 用户页用可点击脚注；完整映射保留在内容与证据文件 |
| journal.py add 拒绝没有假设的报告 | 解释型研究被迫制造预测问题 | 分开研究报告归档与可选预测登记 |
| 缺统一图表数据与报告结构 | HTML、图片和文字可能分别生成、数字漂移 | 引入 report.json、datasets.json 与固定渲染器 |

现有来源分层、check_claims.py、反方审查、forecast.py 和历史复盘继续保留；它们分别承担证据约束、判断挑战和可选预测，不占据默认阅读页的主线。

## 3. Last 30 Days 的复用边界

| 能力 | 处理方式 | 适配要求 |
|---|---|---|
| 多平台社区检索、帖子与评论获取 | 继续调用外部引擎 | 记录引擎版本、来源可用性、查询与运行深度 |
| 去重、重排、主题聚类、代表内容选择 | 消费并保留其结果 | 将主题对应到本次研究问题；不把热度分当事实可靠度 |
| 可用来源诊断、薄结果补查、来源状态 | 借鉴并接入研究调度 | 区分未配置、无结果、部分成功、超时和失败 |
| cluster-first 的综合方法 | 借鉴方法 | 先按议题合并材料，再按投资相关性组织；社区讨论量不决定正文重要性 |
| 缓存后重新输出不同格式 | 借鉴设计 | 换格式重渲染已有研究；更新截点才重新取证 |
| 社区写作模板、HTML renderer | 自建投研版本 | 以研究判断、可计算数据、预期差与观察条件为中心 |

首版不整套复制或 fork Last 30 Days。适配器隔离版本差异，保留原始返回，建立字段兼容测试；引擎不可用时降级到可访问的公开社区检索。若以后复制具体源码，保留对应许可并核查第三方部分。

## 4. 端到端用户流程

1. 理解问题：提取对象、研究任务、时间窗口、比较基准、深度和输出偏好。用户未指定“最近”时，首版默认最近 30 天，并在报告标明实际交易日期与截点。只有歧义会改变研究对象或结论时才澄清。
2. 形成研究计划：把问题转成必须回答项、需要的数据、适合的图表和待检验解释。例如“为什么跌”必须先核实跌幅与基准表现，再检查公司、行业和宏观事件。
3. 检查能力：确定本次可访问的来源、权限与数据新鲜度，选择取证路径。常规研究默认标准深度，不能悄悄使用 quick 并声称完整覆盖。
4. 并行取证：官方与新闻、行情与预期、社区线索按独立任务获取；调用规模随问题复杂度调整。
5. 标准化与计算：统一主体、日期、单位、财季、指标口径和来源关系。用脚本计算收益率、回撤、环比、预期差等，保留输入和公式。
6. 综合分析：筛选最重要的变化，比较候选解释，形成 3–5 个核心发现与下一步观察条件。
7. 双重审查：检查证据与计算，也检查是否真正回答用户、判断是否有信息价值、最强反方是否会改变结论。按缺口定向补查，默认最多两轮。
8. 生成交付：冻结内容与数据，渲染 HTML 和文字，检查图表、链接与页面，在本地归档并交付文件。

完整结果、部分完成和无法回答要有明确状态。某来源失败时仍可交付有支持的部分；缺少决定核心答案的数据时，明确哪个答案尚未得到。换格式、重渲染或失败重试均不得重复登记预测。

## 5. 从社区取证扩展到多源研究

### 5.1 官方披露：业务实际发生什么

美股首批接公司 IR 与 SEC 文件，获取财报、指引、业务分部、管理层解释、公告日期和下一事件。结构化保存期间、币种、单位、GAAP/non-GAAP、实际值/指引值及修订版本。

不能只抓几句财报摘要。按问题抽取连续期间的关键指标，才能回答变化。例如增长问题看收入与分部，增长质量问题再看利润、现金流和应收，不能对所有公司固定塞同一组数字。

### 5.2 行情与基准：市场怎样变化

建立行情提供方接口，首版接一个经核实可访问、使用方式合适的主源和一个回退源。支持历史价格、成交量、基准指数或行业比较。

记录交易所时区、交易日期、盘中/收盘、价格/总回报、复权口径和公司行动。对齐共同交易日期；缺失交易日不补零、不画成零价格。个股与基准的差值称相对表现，不直接称因果贡献。

### 5.3 预期与估值：现在的价格在期待什么

获取可核实的一致预期、预期修订、公司指引与估值指标。明确调查或数据日期、样本范围、财季和分母口径。公司指引、分析师预期和模型情景各自标注。

公开资料不足时显示该模块的数据缺口，不用管理层目标冒充市场共识，也不用社区看多比例补齐。付费供应商与凭据单列为依赖，按实际可用性接入，不在首版承诺全部覆盖。

### 5.4 新闻与行业：解释发生了什么

建立事件时间线，区分事件发生时间、发布时间、市场反应时间；追到首发并合并转载。必要时扩展到客户、竞争对手、供应链和政策变化。

“为什么跌”比较公司特有变化、行业共同变化和宏观背景。按证据支持程度排列解释，不凭空分配“某原因贡献了 40% 跌幅”。

### 5.5 社区：发现分歧和待核实线索

保留议题、代表帖子、原话、反对意见、互动与抓取时间。社区观点若包含可验证事实，转交官方或新闻渠道核查后才进入事实层。

有足够可比样本才展示讨论变化；没有稳定抽样、历史基线和覆盖记录时，不输出看似精确的“市场情绪指数”。

## 6. Agent 与程序的职责

继续使用现有插件与宿主的工具和子 Agent 能力。首版无需引入独立服务、额外 API 密钥或托管 Agent 平台。

| 角色 | 职责 | 输出 |
|---|---|---|
| 主研究 Agent | 理解问题、计划、分配取证、决定补查与交付 | request、plan、运行状态 |
| fact-collector（扩展） | 官方、媒体、可访问的预期材料；按模块返回证据 | 证据条目、事件、缺口 |
| 行情与计算工具（新增） | 读取行情与指标、执行确定性计算 | 数据集、公式、结果与口径 |
| community-scout（扩展） | 调用 Last 30 Days，保留主题与覆盖 | 社区主题和来源状态 |
| 研究综合职责（新增） | 按重要性选信息，建立解释、反方与观察条件 | 结构化研究稿 |
| red-team（保留） | 挑战核心判断，指出决定性遗漏与过度推断 | 必须修正的问题及补查建议 |
| 编辑职责（新增） | 检查是否回答问题、标题和图表是否抓重点 | 可交付内容稿 |
| 渲染与校验工具（新增） | 根据固定模板渲染、检查引用/数据/布局 | HTML、Markdown、可选 PNG |
| forecaster（可选） | 在问题确实需要预测时生成概率 | forecast.json |

综合与编辑最初可由主 Agent 分步骤完成；“职责”不等于每一步都启动一个子 Agent。取证适合并行，内容审查依赖研究稿，渲染依赖冻结内容。只有评测显示独立调用带来收益时再增加角色。

## 7. 内容契约：把有证据的材料变成有价值的报告

每个核心发现包含：
- 判断：一句直接回答用户问题的话。
- 重要性：为什么它会影响对业务、预期或价格的理解。
- 依据：事实、计算、来源观点或推断的明确类型，以及对应证据 ID。
- 机制：它如何联系到收入、利润、现金流、估值或事件结果。
- 反方与边界：最强替代解释，或真正影响判断的关键缺口。
- 更新条件：下一次观察什么，会使判断增强、减弱或被推翻。

编辑规则：
1. 开头先回答问题，不先介绍研究方法。
2. 按本次问题的重要性排序，通常保留 3–5 个发现；资料不足时少写，不凑数量。
3. 选出更受支持的解释并说明理由，不把所有可能性等权排列。
4. 直接事实、来源观点和研究推断保持可区分；研究判断可以明确，但支持范围必须匹配。
5. 同一限制只在影响判断的位置说明，完整采集缺口集中展开。不能把决定性缺口藏进附录。
6. 事实句和推断仍绑定账本；用户页使用轻量脚注与展开内容，避免到处出现内部编号和流程记录。
7. 反方审查用于修正主判断，不整段搬到正文形成免责声明墙。
8. 只有用户问题需要概率，且事件定义、结算来源和期限明确时，才进入预测流程。一般解释报告可以没有假设和概率。

## 8. 数据与产物结构

建议每次研究建立独立 run 目录，避免 tmp-* 在并行和重试时覆盖：

```text
journal/<run_id>/
  request.json          # 原始问题、研究任务、范围、偏好
  plan.json             # 必须回答项、取证与图表计划
  sources.json          # 原始出处、时间、来源关系、获取状态
  claims.json           # 现有证据账本，按兼容规则扩展
  datasets.json         # 图表与计算使用的数据、单位、期间
  calculations.json     # 输入引用、公式、结果、舍入规则
  report.json           # 标题、直接回答、发现、图表与引用绑定
  checks.json           # 证据/计算/内容/页面检查与缺口
  report.html           # 主交付
  report.md             # 同源文字版
  preview.png           # 按需的一页摘要
  forecast.json         # 仅预测任务存在
  manifest.json         # 版本、截点、状态、产物指纹
  raw/                  # 必要的原始返回，不保存凭据
```

这些是建议新增的文件，不是当前已有实现。

report.json 只描述内容和组件类型，不允许夹带任意执行脚本。图表绑定 dataset_id，发现绑定 claim_ids；计算结果再关联输入数据或证据。渲染器读取已经确定的数值，不自行重新研究、改数字或补结论。

保留现有 memo/forecast 账本的读取兼容。历史报告不重新评分、不自动迁移为新预测。研究报告归档成功与预测登记成功分别记录；同一研究的 HTML、文字和图片共享内容版本。更新研究生成新版本，保留旧截点，能说明新增证据和判断变化。

## 9. HTML 阅读与图表设计

默认页面提供三个阅读层次：

- 首屏：直接回答、2–4 个重点数字、最重要图表或对比，以及当前主判断。
- 主文：3–5 个核心发现、关键事件、业务或预期的变化、下一步验证条件。
- 展开层：来源原文与链接、计算口径、社区代表讨论、覆盖情况、完整证据。

页面组件按问题选择，不是每份报告都显示全部栏目：

| 研究任务 | 首选内容与图形 |
|---|---|
| 最近为什么涨跌 | 个股与基准走势、事件时间线、候选解释与支持证据 |
| 财报怎么样 | 实际/预期/指引对比、关键业务指标变化、后续指引 |
| 业务增长质量 | 收入、利润、现金流的独立图或对照表，指标口径一致 |
| 行业主题 | 产业链关系、受影响环节、已验证与待验证信号 |
| 事件概率 | 规则、市场定价与时间变化、情景条件；概率来源清楚 |

图表约束：一张图回答一个问题，通常 1–3 张核心图足够；真实数据不足时用文字或表格。每图给出单位、期间、来源、截止时间和数据表入口。趋势用折线、规模比较用条形、实际对预期用对照点图或表格、事件用时间线。不同量纲分图，不使用双轴制造相关性。

HTML 使用固定组件与本地内嵌资源，优先 SVG；具备移动端布局、悬停/键盘读数、来源跳转、展开证据和打印样式。首版不依赖远程字体、CDN 或外部追踪。对网页原文转义，限制链接协议；图表数据不能作为可执行 HTML/JS 插入。

PNG 是同一 report.json 的专门摘要布局，保留截点与关键限定；不把长网页硬缩成看不清的图片。HTML 是可阅读的本地成品，生成不等于发布外站。

## 10. 质量验收

将“证据符合规则”和“报告值得读”分开验证。以下是拟议标准，需在正式 Issue 中确定后执行。

### 自动检查

- 所有正文引用与图表数据引用可解析，不出现孤立或不存在的证据 ID。
- 关键计算按冻结输入重算一致；覆盖直接舍入、百分比/百分点、财季、复权、基准对齐与缺失值。
- 事实层级符合规则，转载不算独立来源；推断引用其依据。
- 数据时间和研究截点可解释；不能把后取得的实时快照当历史快照。
- 同一内容版本的 HTML、文字与图片中，共有数字和核心判断一致。
- 无假设的解释报告可归档；预测仍执行原有概率与结算校验。
- 断网能打开主交付，无外部资源依赖、浏览器错误、截断或横向溢出。
- 来源部分失败、全部失败、引擎缺失、无预期数据、渲染失败和重试均有覆盖。

### 内容与阅读验收

- 用户明确提出的每个问题都有回答，或有一个明确、具体的未解决项。
- 首屏能识别“发生什么、当前更支持什么解释、接下来关注什么”。
- 每个核心发现能回答“为什么重要”，避免只列财务数字或热帖。
- 有研究判断时，能追到证据与机制；证据不足时把结论范围收窄到可支持的部分。
- “为什么跌”不能只有最后一天新闻或财报预测；“财报怎样”不能只有股价图。
- 在同一冻结证据上与旧版盲比，检查回答完整度、信息优先级、判断价值和阅读负担。模型评分辅助人工，不代替用户阅读。

### 回归题集

首版准备约 10–15 个固定案例，包含 NVDA 近期下跌、财报超预期但股价下跌、无显著新闻的行情变化、来源互相矛盾、官方不可访问、社区稀少、无可靠一致预期、无需预测的解释问题、价格口径差异和 HTML 移动端长标题。另保留一组未参与模板调优的案例，用于检查能否泛化。

冻结数据测试渲染与计算，实时取证另跑集成冒烟。记录实际耗时、调用量、失败率和费用可观测数据，再制定性能预算；当前不承诺尚未测量的延迟与成本。

## 11. 分阶段实施

| 阶段 | 交付与主要改动 | 完成条件 | 依赖 |
|---|---|---|---|
| P0 内容与页面样例 | 用已有 NVDA 证据手工形成 report/datasets 样例、HTML 与同源文字；确定首屏、发现结构与图表规范 | 用户能从成品快速读出变化、主判断和观察条件；逐项可追溯；不重新取证 | 现有研究材料 |
| P1 输出链路 | report schema、渲染器、页面检查、无预测报告归档；修改 memo 模板与 journal 接口兼容 | 同一输入稳定产出 HTML/文字，可处理无假设、缺数据与渲染失败 | P0 验收后的内容契约 |
| P2 多源研究与计算 | 任务路由、行情/官方/预期/新闻适配；Last 30 Days 主题与状态保留；计算工具 | 近期走势、财报解读、市场预期三类任务都有必要数据；有覆盖与降级记录 | P1 契约与数据可用性 |
| P3 一问到底 | 主 Agent 调度、综合与编辑步骤、定向补查、可选预测、自动交付与归档 | 固定题集端到端完成；与旧版盲比；证据、内容、页面三类验收分别达标 | P1/P2 |
| P4 按使用反馈扩展 | 宏观/主题/A/H 股等专用模块，历史对比、按需更新与持续跟踪 | 每增加一类来源或任务，补对应口径与回归案例 | 稳定的 P3 |

对用户发布的首个完整版本应覆盖 P0–P3。P0/P1 可以提前评审页面和内容，不能标成“全自动研究已完成”。日期和人天在确认实际数据源、运行环境与工程负责人后估算；以上是依赖顺序与验收里程碑。

推荐先做 P0：用已完成的 NVDA 研究验证“什么内容值得出现在第一页”，再固定机器契约和自动化，减少把不理想的报告格式程序化的返工。
