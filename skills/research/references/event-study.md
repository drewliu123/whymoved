# 事件研究与参考类分布

## 什么时候用

研究里常说「历史上这类事件之后怎么走」。这句话要么是印象，要么是样本。`event_study.py` 让它在**事前选定的样本**上变成可核对的分布：

- 事件类型明确（例如「指引下调」「ETF 连续净流出 5 日后转正」）；
- 每条样本有事件日期与价格序列；
- 窗口与样本规则在跑之前定好，不是跑完再挑。

它回答「参考类在过去发生了什么」，不回答「这次会发生什么」。

## 输入

```json
{
  "schema_version": 1,
  "event": "虚构事件：指引下调",
  "window": {"before": 5, "after": 10},
  "samples": [
    {"id": "E1", "date": "2025-05-15", "label": "FY25 指引下调",
     "claim_ids": ["C1"],
     "prices": [
       {"date": "2025-05-08", "close": 100},
       {"date": "2025-05-15", "close": 92},
       {"date": "2025-05-29", "close": 97}
     ]}
  ]
}
```

- `window.before` / `window.after` 是**观测点个数**（通常是交易日），不是自然日。`after` 至少 1，两者上限 250。
- 每条样本的 `prices` 必须按日期严格递增、收盘价为正且有限；`date` 必须出现在该序列里。
- 样本至少两条；`id` 唯一；`claim_ids` 可选，用于把样本接回主张账本。
- 未知字段直接拒绝，避免把别的口径混进来。

## 计算与输出

对每条可用样本：

- `pre_return = close(事件日−before) → close(事件日)`
- `post_return = close(事件日) → close(事件日+after)`
- `total_return = close(事件日−before) → close(事件日+after)`

汇总给出 `n`、`mean`、`median`、`q1`、`q3`、`min`、`max` 与 `positive_rate`（收益为正的样本占比）。窗口覆盖不足、事件日不在序列里的样本进入 `skipped` 并写明原因；可用样本少于两条直接失败——两条以下的「分布」没有意义。

```bash
python3 "$TY_DIR/scripts/event_study.py" "$WORK/events.json" --out "$WORK/event-result.json"
```

## 嵌入报告

同一份输入可以放进 `report.event_study` 随报告归档：校验会核对样本 `claim_ids`、窗口与可用样本数，渲染在附录生成「事件研究」小节（分布表与样本明细）。独立运行与嵌入运行共用同一套校验，字段不需要改写。

## 边界

- **绝对收益，不是超额收益**：没有基准调整，也没有行业/市场中性。把它当「同类事件后的绝对涨跌」读，不要当 alpha。
- **不给 p 值**：小样本、手选事件、幸存者偏差都不支持显著性检验。工具刻意不输出 p 值、置信区间或「统计显著」字样。
- **样本事前选定**：文档要求研究者先写清事件定义与纳入标准。跑完再删样本就是数据挖掘，工具无法阻止，但产物会留下完整样本与 `skipped` 记录，便于审查。
- **窗口是观测点**：不同标的交易日历不同，「5 个观测点」在每条样本里对应不同自然日长度，这是有意为之——避免长假造成的假波动。
- **不预测**：参考类分布是背景，不是概率。正文若要给方向或区间，仍须按竞争解释与区分检验写清楚依据。

## 在研究流程里的位置

1. **event_forecast 问题**：先定义可验证目标，再用参考类分布校准「这次与历史有何不同」；把样本规则、n 与分布写进正文或附录。
2. **change_explanation**：解释为什么这次像/不像过去同类事件，用分布说明「像」在哪里。
3. **更新研究**：新事件发生后追加样本，保留旧样本与旧结论，不追溯改写。
